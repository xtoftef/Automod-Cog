# Automod Cog - [discord.py]
A simple discord.py Cog implementation to perform some specific automod tasks

Check the [Basic Documentation](dev_notes/BasicDocumentation.md). It's a must for getting the latest info about the current state of the cog.

See the [Changelog](CHANGELOG.md) for what changed recently, the list of fixed bugs, and a step-by-step guide on adding a new automod feature.

## Introduction

Moderation bots like Dyno, Carl and Wick have some very useful automod implementations. However, they do not always have all the things that a server needs. For example, in a particular server I am in, we see embeds and attachments often be used more than what usually is acceptable and there is a difficulty for server staff to control that usage consistently and without bias. 

Which is why an automod suited for this would be ideal.

## System requirements

Below are some requirements for the system to work better and remain reusable.
**Mandatory requirements:**
- Use discord.py's "Cog" class. Cogs are kind of like plug-and-play components for a bot instance using discord.py. Using them would mean that they can easily be readapted and implemented in different systems without a need for significant structural change or code modification.
- Separation of concerns. A good practice is to make sure the code is structured and the different core functions of the system are isolated/atomic. This means that if you get a problem with X function of the code, you know exactly where that function or class is and it makes debugging simpler. I usually achieve this by having different classes and functions depending on the complexity of the system and its needs

**Optional but preferred requirements:**
- No hardcoded server and user IDs. Discord bots are usually meant to be usable in more than one server and by multiple users. So, this means that you'd need a persistent but yet dynamic memory for things (well, memory if you want to keep data about some servers or users, such as a config). Though, of course, if the logic of how your program works runs on hardcoded values, then later on it can be shifted to a persistent memory.
- Use persistent memory. Programs only store data at runtime unless you make use of files or other means of storage. Persistent memory can either be really simple or get a bit more complex depending on what you want to achieve. If you want a simple but functional thing, I'd recommend using a JSON file since they're pretty much exactly like python dictionaries (at least for what you'll use them for). The ideal is to use a database (like sqlite) but databases are definitely more complex to setup, particularly if you don't have a lot of knowledge about SQL, and the code quickly gets a lot of complexity just to manage the memory. Which is where I would suggest using an abstract class as your template to implement whichever memory management method you'll use. Say you have a class "BaseAutomodMemory" which simply contains various methods like "get_server_config". Then you'll create a JSONAutomodMemory class which inherits from/implements BaseAutomodMemory. 
- Configurability. It'd be good if servers can fine-tune the automod's values (like how long the cooldown is) or disable/enable the commands. The best way is via a dashboard, but that's tedious, so simple commands that allow server admins to do this is good enough.

## Expected functionality:

Here are the different functions that I would expect the bot to achieve
- global attachment/embed cooldown. Global in this case would mean shared between all users within a specific channel (the scope is within the channel the automod is watching). Now, a cooldown between attachments/embeds is kinda boring and limited and also not fun for users. So, the idea was to make it so that **only X amount of attachments/embeds within a span of Y seconds regardless of who sent it** are allowed. My main thought was to have a sort of queue cache or counter that starts empty and gets incremented when the bot detects a message that contains an attachment/embed. If you allow only X attachments, then the bot will delete any message that contains an attachment/embed IF the cache already has X amount of messages. The cached messages could be removed from the cache after a certain amount of time passed. Each channel would have its own individual counter. NOTE: I haven't figured out how this will work exactly, so the idea i have above might not be this at all and there could be a better option.
- chain prevention. One simple thing is to prevent users from chain replying attachments/embeds (or even stickers). Perhaps getting the logic down for this one, then simply altering the code that detects whether a message has the content that we don't want people chaining with. Like, if people chain reply with normal messages, no issues with that, so that's a false positive to avoid. Example, let's say you have messages M1, M2, M3, M4. If all of them contain an attachment and M4 replies to M3, M3 to M2, M2 to M1, then you essentially have a chain of 4 messages and the bot should flag it. If the messages were not replying to each other, then the bot wouldn't flag it. If M2, M3, M4 ALL reply to M1 (M1-M2, M1-M3, M1-M4) then the bot would not trigger either. The automod should of course work with different values

## More on best practices:

Making readable AND maintainable code is difficult, and often times a headache to start the system rather than just doing whatever you feel like works. For example, for a quick prototype, you might opt for a single file with thousand of lines where everything works together. It might be faster to develop at first but on the long run it'll be a pain to maintain, debug, test or improve or add features to. In contrast, someone might spend more time designing the system's architecture, spend time making abstract classes, data models/dataclasses and apply a lot of type checking. But in the end, that code would be a lot more maintainable and easier to expand in the future. So below are my personal recommendations on best practices that I learned from personal experience. DISCLAIMER: I don't know everything, I still have much to learn about it and some of these things may not be the best, but from what I've learned, they do help and work pretty well usually.

- Use type checking. Type checking avoids a lot of headaches when you try to debug. Of course, it takes a bit more effort to clear out all the type errors, but in the end you gain a lot from it and it helps your program run more predictably. Ensuring that functions have defined parameter types and return types will help a lot.
- Use abstract classes. Of course, these are not always necessary. But it really depends on the vision that you have for the program. Abstract classes are particularly powerful and useful for when you want to give more flexibility to future developers if they want to change a particular thing. A very simple example is, say you have an engine class that handles the main logic and it uses a memory component to access your various files or persistent memory. I found it good to have an abstract class with some abstract methods for the memory, so that today, i might use a JSON file to store the things, and another day I'll maybe use a database. Since the engine depends on the abstract class, the engine shouldn't care about how the data is fetched but rather only cares about getting the data. So, the inner working of the memory class might change, but to the engine class, it appears always the same. I find this approach particularly good for scalability.
- Use docstrings for documentation. It's usually good practice to use Python docstrings to describe what a function/method does. I personally usually use Google-Style docstrings, but a good read on them can be found there: https://realpython.com/how-to-write-docstrings-in-python/
- Find a good balance. A lot of the things i said above can be very useful, but if they're overused or used where it's not needed, they'll turn back against you. I'm a huge fan of splitting logic across files, since it makes it more manageable. But let's be honest, you don't really need 10 files each for one class or 100 lines of code, it essentially dilutes your system a lot more than necessary. So, what I often do is start coding in one file and then move things to their own files later on if i see it needed.
- Use clear names and consistent naming. If you go with a particular way of naming your variables, classes and function; stick with it. It'll make keeping the flow of the code a lot clearer. Also avoid using obscure names while also trying to avoid excessively lengthy names (i still struggle with that 2nd part). If you feel like a function's name is already long enough, just add a docstring to explain what it does a bit more in detail.
